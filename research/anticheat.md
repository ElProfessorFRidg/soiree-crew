# Recon-AntiCheat report

Scope: AC-01 to AC-10, plus TER-02/TER-03, RANK-06/RANK-07, SYNC-04/SYNC-06, SEC-03/SEC-06 where they touch anti-cheat. Defensive research only: bypasses are named by class, never described as procedures. All sources read on 2026-10-26 unless stated otherwise. Source tags `[Sn]` refer to section 8.

---

## 1. Summary

1. **iOS `isSimulatedBySoftware` catches almost nothing that matters.** Apple DTS confirmed in October 2025 that the flag is set only for Core Location's own simulation (Xcode GPX), and that third-party spoofing tools "will not have access to set that API flag" [S2][S3]. Treat it as a cheap tripwire for casual cheaters, not as a defence. On iOS, server plausibility and physical corroboration carry the load.
2. **Android `isMock()` is more useful but trivially hidden on a rooted or hooked client.** It flags test-provider locations (developer-options mock apps) [S13]. Because it is cheap and its false-positive rate is low, it earns a high weight, but it must never reject an event on its own.
3. **Attestation is now cheap to add in Expo.** `@expo/app-integrity` wraps App Attest (iOS) and Play Integrity Standard requests plus Android hardware key attestation (Android) [S29]. `expo-location` already exposes a `mocked` boolean mapped to `isSimulatedBySoftware` (iOS) and `isMock()` / `isFromMockProvider()` (Android). I verified this in the source [S28]. Two gaps still need native code: `isProducedByAccessory` is not exposed, and no React Native BLE library we found supports the **peripheral** role. The most-used one, `react-native-ble-plx`, says it does "NOT support communicating between phones" [S30]. Phone-to-phone BLE (AC-04, JOY-01) therefore needs a small native module whatever the stack.
4. **Play Integrity got stricter in May 2025.** On Android 13+, `MEETS_DEVICE_INTEGRITY` now requires hardware-backed verified boot. `MEETS_STRONG_INTEGRITY` requires a security patch from the last 12 months, and about 14.5% of strong verdicts were lost [S20]. The default quota is 10,000 requests per day across all installs [S16][S19]. That means checks are rationed to check-ins and batch syncs, not every drink.
5. **App Attest is not jailbreak detection.** It proves that a Secure-Enclave key belongs to a genuine instance of our app. Apple itself says a "compromised device" can proxy attestations, and the fraud receipt metric only partly catches that [S9][S6][S35].
6. **IP geolocation is weak in France.** MaxMind reports only 51% of French IPs located within 50 km [S39]. Use country level only, at low weight.
7. **Design consequence:** a risk score in four independent categories: device flags, integrity, spatio-temporal plausibility, behaviour/network. Peer and physical corroboration act as credits. "Rejected as cheating" requires strong evidence from **at least two categories**; everything ambiguous becomes "unverified, ask a friend". A cheater with no friend to vouch earns nothing. Nobody honest gets shamed.
8. **Offline-compatible replay protection is possible.** Use device-bound signatures (App Attest assertions and Keystore keys are generated locally), a pre-fetched "nonce book", monotonic-clock timestamps and per-event idempotency keys. Offline events count for BAC and personal stats at once, and score only after server checks (AC-08, SYNC-06).

Platform background:
- Android `getAccuracy()` is the 68th-percentile horizontal radius [S13]. gps.gov gives about 4.9 m for smartphones under open sky, degrading near buildings, indoors and through multipath [S38]. A bar is the worst case, so poor accuracy must never count as suspicious.
- iOS has no public API for "Developer Mode enabled", and none for "external location provider" [S2][S43].
- MASVS v2 resilience controls are short: R-1 "validates the integrity of the platform", R-2 anti-tampering, R-3 anti-static analysis, R-4 anti-dynamic analysis [S25]. MASVS says resilience "must not be used as a substitute for proper security architecture" and "the absence of these measures does not in itself constitute a vulnerability" [S25]. Relevant weaknesses are MASWE-0051 (root/jailbreak), 0053 (emulator), 0054 (device attestation), 0056 (app attestation), 0058 (runtime code integrity), 0064 (debugger) and 0065 (dynamic analysis tools) [S26]. The v1 tests MASTG-TEST-0045/0088 are deprecated; v2 tests include MASTG-TEST-0240, 0241 and 0324 [S27].
- Precedent: Niantic's Pokémon GO three-strike policy (July 2018) treats GPS spoofing and unauthorised clients as cheating. Strike 1 is a 7-day degraded experience, strike 2 a 30-day suspension, strike 3 a permanent ban, with appeals [S34]. For us that suggests a **temporary, reversible consequence first**, which matches AC-09. I could not fetch Niantic's current policy page (404), so I could not confirm whether it changed after 2018.

### 2.2 Server-side plausibility checks (AC-03)

Rules for every check:
- Use **server time** and the monotonic-derived event time (2.6), never the raw device wall clock.
- Subtract both fixes' accuracy radii before computing any distance.
- Only compare events inside one party or a 12 h window.
- Every value below is a remote-config default (2.4), to be calibrated in the AC-10 field test.

| Check | Rule (default) | Points | Category | Rationale / false-positive guard |
|---|---|---|---|---|
| Venue geofence | `distance(fix, venue) − accuracy ≤ radius` (radius 75 m by default, per-venue override for big clubs or terraces) | Fail → **not a cheat**: "you don't seem to be at X" (invalid, no score, no shame) | Precondition | Being elsewhere is not cheating |
| Accuracy too poor | `accuracy > 150 m`, or approximate permission [S14][S10] | 0 points; status unverified (reason: imprecise) → ask for corroboration | Precondition | Basements and old phones must not be punished |
| Impossible travel, strong | effective speed `(d − acc1 − acc2)/Δt > 250 km/h` with `d > 20 km` | +45 | Plausibility | No ground transport in a night out reaches that |
| Impossible travel, medium | 130-250 km/h with `d > 5 km` | +20 | Plausibility | Motorway taxi is possible, so this alone leads only to unverified |
| Coordinates identical across fixes | Two check-ins at different times with lat/lon equal to 1e-6° (≈0.1 m) | +30 | Plausibility | Real GNSS jitters at that precision. Works on keyed hashes, so raw GPS is not kept (5. SEC-06) |
| Coordinates equal to the venue pin | Fix equals our stored venue coordinate to 1e-5° (≈1 m) | +25 | Plausibility | Typical of a dropped pin; an honest fix lands on the pin by pure chance only rarely |
| Frozen accuracy | ≥5 consecutive fixes with identical accuracy (to 0.1 m) and moving or rounded coordinates | +15 | Plausibility | Assumption A-AC-3, to calibrate |
| Too-perfect accuracy indoors | accuracy ≤ 2 m on ≥3 consecutive indoor-venue check-ins | +10 | Plausibility | Below open-sky phone typical (4.9 m [S38]); weak |
| Stale fix | fix timestamp older than 120 s at event creation | 0 points; client must refresh the fix (UI) | Precondition | Cached fixes are normal; we just ask again |
| Wall clock vs monotonic time | `|wall_event_time − monotonic_derived_time| > 5 min` | +20 | Behaviour | Detects clock tampering (AC-10). Skipped when the boot ID changed (reboot) |
| Device clock vs server (online events) | `|device_now − server_now| > 5 min` | +5 | Behaviour | Many phones drift slightly; weak |
| Opening hours | Check-in more than 30 min outside known opening hours | +15 | Plausibility | Unknown hours give 0. Private and house parties are exempt (they use QR) |
| IP country | IP country ≠ venue country, and not a roaming carrier | +10 | Network | Country only, because city-level is unreliable (51%/50 km in France [S39]) |
| Datacenter / VPN ASN | Egress from a hosting ASN | +5 | Network | VPNs are legitimate privacy tools |
| Venue hopping | Check-in attempts at ≥3 distinct venues within 10 min | +20 | Behaviour | Also rate-limited (2.6) |
| Machine cadence | ≥5 events with inter-arrival jitter < 1 s, or scripted client fingerprint | +15 | Behaviour | Request patterns no human produces (AC-03) |
| Multi-account device | ≥3 accounts on one attested key or device in 30 days; Play `deviceActivityLevel` = LEVEL_4 [S17]; App Attest risk metric above the calibrated baseline [S6] | +15 | Integrity | Families can share a phone, so this is weak |

TER-03 rules applied before scoring: one counted check-in per venue per party, and at least 20 min (configurable) between two counted check-ins of the same user.

### 2.3 Peer corroboration, BLE handshake, rotating QR, live photo (AC-04)

**Peer confirmation**
- Passive: another crew member has an *accepted* check-in at the same venue within ±20 min → credit −20.
- Active: one-tap "I'm with them". The confirmer must have an accepted check-in at that venue (or a BLE handshake with the target) within ±30 min → credit −30, at most 2 confirmations counted per event.
- Limits against collusion:
  - a confirmer can give at most 8 confirmations per party;
  - mutual confirmation rings (A↔B always and only with each other, with no other signal) are logged for the admin;
  - every confirmation is visible in the timeline, which carries a social cost.

**BLE mutual handshake (also JOY-01 "Cheers")**

Platform constraints that drive the design:
- iOS peripheral advertising supports only two keys, local name and service UUIDs, in 28 bytes. In the background, "the local name isn't advertised and all service UUIDs are in the overflow area", which only an iOS device "explicitly scanning for them" can discover [S11].
- iOS background scanning needs the `bluetooth-central` mode and explicit service UUIDs, and scan options "have no effect" in the background [S12].
- So there is no custom payload in iOS advertisements, and background discovery between iOS and Android is unreliable. Assumption A-AC-5: Android cannot read the iOS overflow area.
- **Design: a foreground, gesture-driven handshake.** JOY-01 already has both phones open.

Handshake:
1. When a party starts, the server gives each member's device a per-party secret `K = HKDF(server_master, user_id ‖ party_id ‖ install_id)`, cached for offline use.
2. Token: `T(w) = trunc16(HMAC-SHA256(K, w))` where `w = floor(t / 60 s)`. Tokens rotate every 60 s, much faster than the ~10-15 min rotation of Exposure Notification identifiers [S40], because we prove co-presence at a moment, not over a day.
3. Both phones advertise one fixed app service UUID. The phone that finds the other connects over GATT. Each writes `{T(w), fresh 16-byte nonce}` to the other and reads the peer's value back. Each records `(own T, peer T, peer nonce, RSSI, monotonic time)`.
4. Each phone queues a signed `proximity_observation` event (2.6), which works offline.
5. The server accepts proximity only if **both** observations arrive: the tokens recompute for windows within ±1, the nonces cross-match, the event times are ≤ 90 s apart, and both RSSI ≥ −80 dBm (configurable). A one-sided record is ignored.
6. Credit: −50 for a check-in when the peer has an accepted check-in at that venue within ±30 min.

Limits:
- Two colluding friends can relay radio frames over the internet within the window. RSSI and the time limit raise the cost; social visibility does the rest.
- BLE does not work with Bluetooth off.
- If BLE fails, the fallback is a **phone-to-phone QR** with the same token.

Android permissions [S15]:
- API 31+: `BLUETOOTH_SCAN`, `BLUETOOTH_ADVERTISE` and `BLUETOOTH_CONNECT` (runtime, "Nearby devices" group). `BLUETOOTH_SCAN` can carry `neverForLocation`, because we do not derive location from scans. The trade-off is that some beacons are filtered, which does not affect our own service UUID.
- API ≤30: `BLUETOOTH` and `BLUETOOTH_ADMIN` with `maxSdkVersion="30"`, plus `ACCESS_FINE_LOCATION`.
- `ACCESS_BACKGROUND_LOCATION` only for background scans on API 29-30, which we avoid.

iOS needs `NSBluetoothAlwaysUsageDescription`. Background modes are not needed for the foreground design.

Library gap: `react-native-ble-plx` is central only [S30]. Write an Expo Module (iOS `CBPeripheralManager` + GATT service; Android `BluetoothLeAdvertiser` + `BluetoothGattServer`), or evaluate `munim-bluetooth-peripheral` [S33].

**Rotating QR (house parties)**
- The host's phone shows `party_id ‖ w ‖ trunc16(HMAC(K_host, w))` with `w = floor(t / 30 s)`. It works offline, because K is cached.
- The server accepts `w` within ±1 (≤ 90 s), counts one scan per guest per party, and credits −60.
- The host sees the list of scanned guests, which is a social check.
- Limits:
  - A live video relay inside the window defeats it. Where both phones have location, the guest's fix must be within 150 m of the host's last fix; otherwise the credit drops to −30.
  - A screenshot dies within 90 s.
  - Offline scans are queued and validated with the monotonic event time (2.6).

**Live photo (O-83, AC-04)**
- Camera-only capture in the app, no gallery.
- Upload must follow capture within 2 min (monotonic), or be queued with its capture time if offline.
- Perceptual-hash dedupe against the user's earlier photos catches a reused photo.
- Visible to the crew. One crew "looks right" gives a credit of −25.
- Limit: a photo of a screen. The crew judges.

### 2.4 Risk score (AC-06)

Model: an additive risk score `R = Σ risk points − Σ corroboration credits`, computed on the server for each event. Signals belong to four independent **categories**:
- **F** device-reported location flags;
- **I** integrity;
- **P** spatio-temporal plausibility;
- **B** behaviour and network.

Credits come from **C** corroboration.

Integrity and flag weights (plausibility and behaviour weights are in 2.2):

| Signal | Points | Cat. |
|---|---|---|
| Location `mocked` = true on the check-in fix (Android `isMock`) | +50 | F |
| Location `mocked` = true on iOS (`isSimulatedBySoftware`) | +50 | F |
| `isProducedByAccessory` | +5 (logged, otherwise neutral) | F |
| App Attest supported but no assertion | +25 | I |
| Assertion or Play token invalid, counter not increasing, `requestHash` mismatch | Request refused as **invalid** (SYNC-04 definitive), logged as tamper, +60 to the user's 30-day tamper tally | I |
| Play `UNRECOGNIZED_VERSION` | +40 | I |
| Play no `MEETS_DEVICE_INTEGRITY` (Android 13+) | +20 | I |
| Play `UNLICENSED` / not installed from Play | +10 | I |
| Play `appAccessRisk` contains `UNKNOWN_CONTROLLING` or `UNKNOWN_CAPTURING` | +10 | I |
| Emulator / virtual device | +30 | I |
| Root or jailbreak heuristics positive | +15 | I |
| Hooking framework detected | +25 | I |
| Integrity check **unavailable** (outage, unsupported device, quota exhausted) | 0, record `integrity=unknown` | I |
| Corroboration credits | BLE −50, QR −60, peer passive −20, peer active −30 (×2 max), live photo −25 | C |

Bands (remote config defaults):

| Band | Rule | User sees (FR UI) | Effect |
|---|---|---|---|
| **Accepted** | `R < 30` | nothing extra; the server-confirmed animation plays (SYNC-02) | Scores (TER-02) |
| **Unverified** | `30 ≤ R < 70`, **or** `R ≥ 70` with risk from only one category, **or** any credit applied | "À confirmer : demande à un pote de valider" plus a one-tap request to present crew | No score until corroboration lowers R below 30. Re-evaluated until party end + 6 h |
| **Rejected as cheating** | `R ≥ 70` **and** risk points from **≥ 2 categories** (F, I, P, B) **and** no corroboration credit | "Tentative de triche" (AC-09) | Nothing earned. Recorded and visible (AC-09). Admin can overturn |

Worked examples (defaults):
- Honest user in a basement, accuracy 180 m → precondition "imprecise", R = 0 → unverified until a friend confirms.
- Honest LineageOS user: no device integrity (+20) → R = 20 → accepted.
- Android user with a mock app: mocked (+50, F) and pin-exact coordinates (+25, P) → R = 75 over two categories → rejected.
- Hidden-flag teleporter: speed (+45) and pin (+25), both in P → R = 70 in one category → unverified. They earn nothing unless a friend vouches.

Kindness rules (these protect the night):
1. **Automatic re-evaluation can only upgrade** a verdict, for example when a late peer confirmation or a config change arrives. Downgrading a past accepted event needs an explicit admin or ops action.
2. Every verdict stores `config_version` and a signals snapshot without raw GPS, so scoring is replayable (AC-01).
3. Missing signals, such as an integrity outage or approximate location, never add risk. They only remove the ability to be "accepted" without corroboration.
4. Shame (AC-09) applies only to "rejected". The first rejection gives a 7-day badge (Niantic's first-strike length [S34] as precedent). Repeat offender: 3 rejections in 30 days → flag to the crew admin.

### 2.5 Drink fraud rules (AC-07, RANK-06, RANK-07)

Every drink always counts for BAC and personal stats. The rules below only decide whether it is **verified** for leaderboards. Grams are ethanol. France standard drink = 10 g (Recon-BAC confirms per country).

| Rule | Default | Outcome |
|---|---|---|
| Burst, 30 min | Rolling 30 min window > 40 g (≈ 4 French standard drinks) by consumption time | The excess drinks become unverified (`burst`) |
| Burst, 60 min | Rolling 60 min > 60 g | Excess unverified |
| Physiological plausibility | Server BAC model (Recon-BAC: Widmark + absorption + elimination; elimination typically 0.10-0.20 g/L/h [S41]) predicts a peak above the RANK-07 danger cap | Further drinks earn nothing (RANK-07) and the UI moves to adaptive level 3 |
| Retroactive | Consumption time more than 45 min before the monotonic creation time | Unverified (`late_entry`). An offline queue entry is not retroactive when its monotonic creation time matches the consumption time (2.6) |
| Batch | ≥ 3 drinks created within 2 min (monotonic) with consumption times spread over > 30 min | All unverified (`batch`) |
| Outside party | Consumption time before party start − 30 min, or after party end | Personal only, never verified |
| After party closed | Created after the party is closed | Personal only |
| Verified by friend | The confirmer is a party member with an accepted check-in at the same venue, or a BLE handshake with the drinker, within ±30 min, confirming within 2 h | Verified. At most 1 confirmation per drinker per 20 min per confirmer, and at most 20 per confirmer per party |
| Verified by live photo | Camera-only, uploaded within 2 min of capture (or queued), not a perceptual duplicate | Verified once one crew member sees it without objecting for 10 min, or approves it |
| BLE "Cheers" | A handshake within 5 min of the drink, for both participants | Verifies one drink each |

Limits: a friend can confirm a fake drink. That is collusion, it stays visible in the timeline, and the drinking leaderboard is crew-only (COM-03). The numbers are game rules, not health advice. The danger cap stays the overriding rule.

### 2.6 Replay and tampering protection compatible with the offline queue (AC-08, SYNC-04, SYNC-06)

Event envelope (one per queued mutation):
- `event_id`: UUIDv7 = idempotency key. A duplicate returns the stored result, not an error (SYNC-08 "duplicate send").
- `install_id`, `seq`: per-install monotonic counter. Gaps are allowed; regressions are refused.
- `boot_id` + `mono_created_ns` + `mono_sent_ns` from the monotonic clock (Android `elapsedRealtimeNanos` [S13]; iOS equivalent assumed, A-AC-6). Server event time = `server_received − (mono_sent − mono_created)`. This holds whatever the wall clock says, as long as the phone did not reboot.
- `wall_created`: informational, compared in 2.2.
- `prev_hash`: SHA-256 of the previous event of this install. It makes the order of the offline queue tamper-evident.
- `nonce`: taken from a **nonce book**. While online, the server issues 50 single-use nonces, each valid 24 h, and the client consumes one per event. Book empty → `nonce=null`. The event is still accepted for BAC and stats, but it cannot score without corroboration.
- Signature:
  - iOS: App Attest assertion over `SHA-256(canonical payload)`. Assertions are generated locally (Secure Enclave), with a strictly increasing counter [S5]. Assumption A-AC-7: they work offline.
  - Android: hardware Keystore key, attested once through Key Attestation at registration [S22][S29], signs each event offline. When online, one Play Integrity Standard token per **sync batch**, with `requestHash = SHA-256(batch)` [S18], keeps within the 10k/day quota [S19].

Server checks, in order:
1. TLS 1.2+ with pinning (SEC-03).
2. Session auth.
3. Signature and counter valid. Otherwise the request is invalid, a definitive SYNC-04 rejection, never retried.
4. Nonce unused and unexpired (reuse → replay refused and logged).
5. `event_id` dedupe.
6. `prev_hash` chain.
7. Age check: events older than `max_offline_age_h = 24 h` at receipt → personal stats only, no score unless corroborated.
8. Scoring window: party end + 6 h grace, so people who were offline at the end are not punished.
9. Then AC-03/AC-06 scoring.

Rate limits (token bucket per user + install):
- check-in attempts 6/h;
- drink events 30/h;
- proximity observations 60/h;
- confirmations 20/h.

Over the limit → HTTP 429, a *temporary* error in SYNC-04 (backoff), never a cheat verdict. Grouped rejection messaging follows SYNC-06.

Limits:
- A fully compromised device can sign fake events with its own legitimate key. Signatures prove the source, not the truth, which is why plausibility and corroboration exist.
- App Attest keys do not survive reinstall, restore or migration [S4]. The server re-attests and does not treat a new key as fraud by itself.

## 3. Decisions proposed

1. **Defence in depth with the server as judge (AC-01, AC-06).** Use the four-category risk score with the two-category rule for rejection. Reason: published bypasses exist for every single signal (Sections 2.1, [S2][S9][S37]). The two-category rule plus corroboration credits keeps false positives off honest users.
2. **Use `expo-location` `mocked`** if the stack is Expo/RN. Add a ~50-line native module for `isProducedByAccessory`. Reason: verified mapping in source [S28].
3. **Use `@expo/app-integrity`** for App Attest, Play Integrity Standard and Android key attestation. Pin the version: the search summary called it alpha with frequent breaking changes, and the SDK 58 page does not say so either way (A-AC-1). Verification runs on our server. On Android 13+, accept `MEETS_DEVICE_INTEGRITY` as "good". Do not require STRONG, which lost about 14.5% of responses in May 2025 [S20].
4. **Ration Play Integrity calls**: one at session start, one per check-in, one per sync batch. No call per drink. Request a quota increase before launch [S19].
5. **Build a BLE peripheral native module** (iOS + Android) for the foreground handshake, with a phone-to-phone QR fallback. Reason: no maintained RN library supports the peripheral role [S30], and iOS background advertising cannot carry a payload [S11].
6. **Root/jailbreak/hooking: start with `jail-monkey`-class in-house heuristics at low weight.** Evaluate freeRASP only after Recon-Security reviews its data flow to Talsec (GDPR, SEC-08) [S32].
7. **Monotonic-clock event timing plus a nonce book** for offline replay protection (2.6).
8. **Upgrade-only automatic re-evaluation.** Shame only on "rejected"; 7-day first badge; admin overturn feeds calibration.
9. **IP geolocation at country level only** [S39].
10. **No hard block on integrity failure** (AC-05). Failing integrity only adds risk. Integrity unavailable adds nothing.

## 4. Assumptions

- **A-AC-1**: `@expo/app-integrity` is production-usable at the SDK we pick. Based on the SDK 58 docs [S29]; a search summary said "alpha, frequent breaking changes". Verify: changelog and npm tag at stack decision.
- **A-AC-2**: iOS `sourceInformation` is nil for ordinary fixes. Based on a comment in the expo-location source [S28]. Verify on a device.
- **A-AC-3**: Real fixes rarely repeat accuracy to 0.1 m five times in a row, or match a pin to 1e-5°. Unsourced, from general GNSS knowledge. Verify with RT-20 data.
- **A-AC-4**: Thresholds of 250/130 km/h, 75 m radius and 150 m maximum accuracy suit European nightlife. Unsourced. Verify with RT-20 and the venue data from Recon-Maps.
- **A-AC-5**: Android cannot discover iOS background-advertised services (Apple overflow area). Based on [S11] wording ("only by an iOS device"). Verify on devices.
- **A-AC-6**: iOS gives an app-readable monotonic clock and boot session identifier usable for event timing. General knowledge (e.g. `ProcessInfo.systemUptime`), not sourced here. Verify in Apple docs.
- **A-AC-7**: App Attest `generateAssertion` works offline (local Secure Enclave signing). Inferred from [S4][S5], which describe no network step for assertions. Verify on a device in airplane mode.
- **A-AC-8**: Play Integrity Standard token requests need network. Inferred from "a few hundred milliseconds" latency [S16]. Verify. If true, hardware Keystore signing covers offline events.
- **A-AC-9**: Play internal and closed testing tracks count as "installed from Google Play" for `LICENSED` and optional labels. Not verified. Verify in the Play Console test setup.
- **A-AC-10**: The red team operates only on our accounts and devices, including our own rooted or jailbroken test device if we choose to have one. Process assumption, confirmed with the user before RT-10.
- **A-AC-11**: DeviceCheck bits persist across reinstalls. Commonly stated but **not verified** in [S8]. Verify in "Accessing and modifying per-device data".
- **A-AC-12**: The Niantic policy cited is from 2018 [S34]; the current text was not reachable. Used only as precedent.
- **A-AC-13**: The described keybox-leak and proxying bypass classes come from community and vendor sources [S36][S37]. Treated as indicative, not verified.
